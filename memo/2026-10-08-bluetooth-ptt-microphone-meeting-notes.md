# GPT Wrapper｜藍牙 PTT 麥克風 Prototype 討論紀錄

- **日期**：2026-10-08
- **主題**：將現有 GPT Wrapper 延伸為具備麥克風、PTT 與 Submit 雙按鍵的實體藍牙裝置
- **文件類型**：會議紀錄／方案探索（非實作規格）
- **專案**：`gpt-wrapper`
- **名詞**：以下統一以 **PTT (Push-to-Talk)** 表示按住說話鍵；對話中有時寫作「PPT Shortcut」。

## 一、背景與最終產品願景

目前 GPT Wrapper 為 Windows Tauri App，使用 ChatGPT WebView 提供語音聽寫、專案分頁、背景待命分頁與快捷鍵操作。使用者希望進一步把主要操作搬到一個**低成本、可攜式的實體藍牙裝置**，而非長期依賴電腦鍵盤。

最終裝置的預期元素：
- **麥克風**：透過藍牙連接 Windows，連線常駐；不需要每次按鍵重新配對或重新建立控制連線。
- **PTT 按鍵**：按住時開始有效收音與 ChatGPT 聽寫，放開時停止有效收音並結束聽寫。
- **Submit 按鍵**：獨立控制訊息送出，避免每次 PTT 放開就自動送出。
- **低操作阻力**：按下 PTT 到真正可以說話的延遲要短，首尾音節不能遺失。
- **低成本與快速試作**：使用者沒有電子電路設計經驗，優先使用現成零件與開發板驗證。

## 二、已決定的事項

1. **使用軟體靜音（Software Mute）** 作為 Prototype 方向，而非要求每次放開 PTT 都關閉麥克風感測器供電。
2. **藍牙連線維持常駐**：待機時音訊應保持就緒；PTT 只是控制是否輸出有效語音，不應每次觸發重新配對。
3. **兩顆獨立按鍵**：PTT 負責聽寫的開始／結束，Submit 負責送出；設計上區分兩個動作。
4. **最終目標仍是實體藍牙裝置**；Android App 可以作為前期體驗驗證途徑，但不是最終產品。
5. **快捷鍵應盡量不與一般鍵盤衝突**：已討論 MIDI；目前技術建議優先評估 BLE GATT 自訂事件，而非直接模擬常見鍵盤組合鍵。這是推薦方案，**尚未正式定案**。

> 軟體靜音代表「待機時不把有效聲音送入聽寫路徑」，**不等同**「麥克風硬體在待機時完全不擷取聲音」。若未來對硬體層級隱私有要求，需要另立需求。

## 三、目標操作流程

| 操作 | 連線 | 音訊輸出 | GPT Wrapper／ChatGPT |
| --- | --- | --- | --- |
| 裝置開機、連線完成 | 維持藍牙連線 | 預設靜音 | 待命 |
| 按下並持續按住 PTT | 不重連 | 放行有效語音 | 啟動目前目標頁籤的聽寫 |
| 放開 PTT | 不重連 | 恢復靜音 | 結束聽寫，等待轉錄文字完成 |
| 按下 Submit | 不重連 | 維持靜音 | 送出已完成轉錄的訊息 |
| 裝置斷線／異常 | 連線中斷 | 停止有效語音 | 強制解除 PTT 狀態，避免卡在錄音中 |

應支援多段 PTT 聽寫後再由 Submit 統一送出；Submit 若發生於轉錄尚未完成時，不能誤送空白或不完整內容，具體策略待定。

## 四、目前專案可重用的基礎

依本次檢視的 `src-tauri/src/main.rs` 與 `src-tauri/src/chatgpt_adapter.js`：
- 目前透過 `Ctrl+0`／`Ctrl+Numpad0` 的 Global Shortcut 收到 **Pressed／Released** 事件。
- 已有 PTT 狀態管理、固定目標分頁、ChatGPT 聽寫按鈕操作及轉錄完成後的自動送出流程。
- App 關閉到系統匣時，已有預先載入的 Standby Tab；背景觸發 PTT 會建立／啟用新分頁，並可填入 Project Message Prefix。
- Settings 已提供 **PTT Auto Submit** 切換；目前預設自動送出，未來雙按鍵模式需和此設定的行為協調。
- ChatGPT 聽寫仍依賴 WebView2、網頁按鈕與麥克風權限；按鍵事件到「實際開始錄音」存在時間差。

因此建議在設計上把 **PTT_DOWN、PTT_UP、SUBMIT** 統一為應用層事件，由 Windows 快捷鍵、Android 或 BLE 裝置共用，而不是為不同輸入來源各自複製聽寫邏輯。

## 五、技術方案比較

### A. Android App（最快驗證使用體驗）
- 畫面提供 PTT／Submit 兩顆虛擬按鈕。
- 可先透過同一區域網路把按鍵事件送至 Windows Wrapper。
- 手機麥克風傳至 Windows，可評估現成工具（例如 AudioRelay）加虛擬麥克風，減少自行開發音訊串流的負擔。
- **限制**：第一版不等於「Android 以標準藍牙麥克風連線」；Wi-Fi Audio Bridge 與正式藍牙路線是兩件事，需避免混為一談。

### B. 第一版實體硬體：BLE 兩鍵控制器＋現成藍牙麥克風
- 使用支援 BLE 的開發板及兩顆按鈕，負責輸出 PTT_DOWN／PTT_UP／SUBMIT。
- 音訊先使用 Windows 可辨識的現成 Bluetooth HFP 麥克風／耳麥。
- Windows 端以音訊 Gate 控制實際聲音通過；可評估虛擬麥克風／虛擬音訊驅動與現成工具。
- 優點是把「藍牙控制事件」與「藍牙音訊」的風險分開，先證明實體操作體驗。
- 缺點是 Prototype 可能暫時由兩個物理裝置組成；音訊 Gate 和虛擬麥克風仍需整合驗證。

### C. 最終單一實體裝置（產品化方向）
- 在同一個外殼中整合兩顆按鍵、麥克風、電源及藍牙通訊。
- 若希望 Windows **直接辨識為標準藍牙麥克風**，晶片／韌體必須支援合適的 Bluetooth 音訊 Profile，例如 HFP 或 LE Audio，且 Windows 主機、驅動與晶片相容。
- `XIAO nRF52840 Sense` 雖有內建 PDM 麥克風和 BLE，**不能因此假設它能直接充當 Windows 標準藍牙麥克風**。若以自訂 BLE 傳送 PCM／壓縮音訊，Windows 端需額外的音訊接收與虛擬麥克風橋接。
- **單一裝置是否為不可妥協要求，尚未由使用者最後確認**；但原始願景明確傾向單一裝置，選型應保留此目標。

## 六、關於 MIDI、BLE HID 與 BLE GATT

- **鍵盤 HID**：最快與現有快捷鍵系統整合，但仍可能與其他軟體的熱鍵產生衝突；F13–F24 比常用按鍵更不容易衝突。
- **BLE MIDI**：可降低普通鍵盤衝突，但 Windows MIDI 裝置接收／相容性會增加 Wrapper 整合工作。
- **BLE GATT 自訂服務（目前推薦）**：設備發送明確的按下、放開、Submit 通知，由 Wrapper 接收；不佔用鍵盤快捷鍵。需處理配對、安全、重連與遺漏釋放事件。

## 七、音訊架構與主要技術風險

初期建議的概念路徑：

```text
藍牙麥克風（HFP）
  → Windows 音訊輸入
  → Audio Gate（PTT 按住：通過；放開：靜音）
  → Virtual Microphone（或等效音訊輸入橋接）
  → WebView2 / ChatGPT Dictation

BLE 雙按鍵控制器
  → Windows Wrapper：PTT_DOWN / PTT_UP / SUBMIT
  → 同步控制 Audio Gate 與 ChatGPT 聽寫流程
```

重點風險：
1. **藍牙已連線不代表 HFP 音訊串流一直啟用**：必須實測待機後第一次說話是否需要額外啟動音訊 Session。
2. **錄音啟動延遲**：目前 Wrapper 仍需操作 ChatGPT 網頁聽寫按鈕；Gate 放行的時間未必代表 ChatGPT 已開始收音，可能丟失第一個音節。
3. **停止時尾音截斷**：放開 PTT 立刻靜音，可能切掉最後一個音節；需決定短暫延後靜音／尾端緩衝策略。
4. **Windows 虛擬麥克風實作成本**：可能需要現成虛擬音訊工具或驅動，不能假設 Tauri 直接提供此能力。
5. **ChatGPT DOM 非公開 API**：既有聽寫按鈕與送出流程可能隨網頁變更。
6. **自動送出邏輯**：現有 PTT 放開後可自動 Submit；雙按鍵操作需要重新定義設定優先順序與轉錄完成判斷。
7. **斷線與例外恢復**：BLE 斷線、App 切換分頁、待命頁載入中、快速短按、重複事件等都不能讓 PTT 卡住。

## 八、建議執行階段（尚未正式排期）

| 階段 | 目的 | 主要產出 |
| --- | --- | --- |
| Phase 1：軟體 UX 驗證 | 先確認兩鍵流程與收音時序 | Android 虛擬 PTT／Submit、Windows 接收事件、可用音訊橋接 |
| Phase 2：實體控制器 | 驗證實體按住／放開、BLE 事件、重連 | BLE 開發板＋雙按鍵，使用現成藍牙麥克風 |
| Phase 3：整合音訊控制 | 驗證常駐音訊、靜音與端到端延遲 | Audio Gate、穩定麥克風來源、完整聽寫與送出流程 |
| Phase 4：單一裝置收斂 | 驗證最終產品可行性 | 支援合適藍牙音訊 Profile 的整合硬體選型、外殼與供電 |

成本僅供早期粗估：Android 試作在已有手機時可低硬體成本開始；兩件式硬體 Prototype 曾估約 **NT$1,000–2,500**（不含開發工時、運費與可能的授權）。**價格、料件取得與相容性均尚未實際採購驗證**，不應視為報價。

## 九、驗收指標（提案，需實測確認）

- 待機至少 30 分鐘仍保持可用，PTT 不因閒置而重新配對。
- PTT 按下後，Audio Gate 目標於約 200 ms 內放行；**ChatGPT 真正開始錄音的端到端延遲要另行量測**，不能把兩者混為同一指標。
- 首字與尾字不明顯被截斷。
- 待機時 ChatGPT 不會收到有效聲音；其他音訊輸入設備不被意外全域靜音。
- Submit 不會搶在轉錄完成之前送出。
- 斷線／頁籤關閉後能解除 PTT 狀態並回到安全靜音狀態。

## 十、尚未決議／後續待確認

1. **最終是否強制單一物理裝置**：原始願景偏向「兩鍵＋麥克風一體化」，最後尚未明確確認；這將顯著影響晶片選型。
2. **第一個實作里程碑**：先 Android 軟體模擬，或直接 BLE 雙按鍵＋現成藍牙麥克風；目前推薦前者先驗證 UX，再做後者。
3. **軟體靜音放置位置**：正式產品偏好在裝置端輸出靜音；現成 HFP 麥克風 Prototype 則可能必須在 Windows Audio Gate 達成。
4. **多段轉錄、Submit 在轉錄期間按下時的行為**：應等待完成、禁用按鍵或顯示狀態；尚未定案。
5. **PTT Auto Submit 設定如何搭配獨立 Submit 鍵**：是否將實體裝置模式固定為手動送出，待決定。
6. **Windows 藍牙音訊硬體支援**：需實測 HFP 連線保持與 LE Audio 支援條件，並依結果決定正式晶片。
7. **配戴或手持形式**、電池續航、充電方式、裝置尺寸與按鍵手感，待後續產品設計討論。

---

**本次結論**：採用「藍牙長連線＋軟體靜音＋PTT 放行／Submit 獨立送出」作為方向；先降低音訊風險、逐步驗證 Android 控制、BLE 實體按鍵與 Windows Audio Gate，最後再收斂成完整藍牙硬體。此文件僅記錄討論與提案，**尚未授權任何程式碼實作**。
